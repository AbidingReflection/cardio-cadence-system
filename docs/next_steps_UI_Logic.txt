I’m continuing work on the `cardio-cadence-system` project, specifically the browser-based Protocol Designer located under:

```text
apps/protocol-designer/web/
```

The basic HTML and CSS shell is already in place. It includes:

* A top application ribbon
* A left Protocol pane
* Two stacked graph panes on the right
* A floating totals ribbon at the bottom
* Separate CSS files for shared layout and individual components

The Protocol pane currently has:

* An `Add Phase` button
* An `Add Block` button
* A dedicated content container that JavaScript can render into

I want to begin the JavaScript architecture now.

## Intended first-version behavior

* `ProtocolModel` owns all phases and blocks.
* Every phase and block has a stable unique ID.
* All mutations happen through model methods.
* External code should not directly mutate the model’s arrays or objects.
* The model emits a generic change event after each successful mutation.
* The UI rerenders the entire Protocol pane after each model change.
* Full rerendering is acceptable for the first version; do not prematurely optimize for partial DOM updates.
* Editor state is separate from protocol data.
* The editor supports these modes:

  * `normal`
  * `insert-phase`
  * `insert-block`
* Entering an insertion mode renders explicit insertion zones.
* Phase insertion zones appear before, between, and after phases.
* Block insertion zones appear before, between, and after blocks within each phase.
* Clicking an insertion zone adds the item at that location and returns the editor to normal mode.
* Pressing Escape cancels insertion mode.
* Final protocol JSON is generated directly from the model.
* UI-only state such as selection, hover, and insertion mode must not be serialized into the protocol JSON.

## Architectural preferences

Keep these concerns separate:

1. Protocol data and mutations
2. Editor state
3. DOM rendering
4. User interaction and event handling

Use stable IDs rather than array indexes when identifying phases and blocks.

The model API will likely need operations such as:

```text
addPhaseBefore
addPhaseAfter
removePhase
updatePhase
addBlockBefore
addBlockAfter
removeBlock
updateBlock
subscribe
toJSON
```

Exact names are still open for discussion.

The likely high-level flow is:

```text
User action
→ event handler
→ model mutation or editor-state update
→ render
```

Both the Protocol pane and future SVG graph renderers should derive their output from the same model and editor state.

Selection should live in editor state so that selecting a phase or block can later highlight the corresponding SVG graph region.

A possible editor-state shape is:

```js
{
    mode: "normal",
    selectedPhaseId: null,
    selectedBlockId: null,
    hoveredPhaseId: null,
    hoveredBlockId: null
}
```

Hover fields are optional for the first version.

## Important constraints

* Use plain browser JavaScript with ES modules.
* No framework is planned at this stage.
* Avoid unnecessary abstractions.
* Prefer readable, explicit code over clever code.
* Keep the first version small enough to understand completely.
* Do not implement drag-and-drop yet.
* Do not implement partial DOM reconciliation yet.
* Do not implement undo/redo yet, but avoid choices that would make it unnecessarily difficult later.
* Blocks should have a `type` field from the beginning, even if only one block type exists initially.
* Keep the hierarchy explicit:

```text
Protocol
→ Phases
→ Blocks
```

Do not create a generic infinitely nested tree.

Before writing code, please review this architecture, identify any important decisions we still need to make, and propose a sensible JavaScript file structure and implementation order.
